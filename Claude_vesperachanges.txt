The thing that overrides everything else

The Problem: Your entire content pipeline has no legitimate source of audio. vespera_backend/main.py uses Spotify's Web API (spotipy) purely for metadata, then lib/services/music_service.dart takes that metadata and does this:

The Fix: There isn't a code diff for this — it's an architecture decision, and it's the one that actually matters. Three real options, roughly in order of how "fundable/acquirable" they leave you:

Pivot to a companion/discovery app. Keep the AI recommendation and UI work, drop in-app playback, and deep-link into the user's existing Spotify/Apple Music/YouTube Music app to play the track. Zero licensing exposure, and it's a legitimate, shippable product category (Musicboard, Setlist, etc. all work this way).
Build on a licensed catalog via a service that explicitly permits third-party streaming apps (this generally requires a real label deal or a distributor partnership — not free, not solo-dev-friendly right now, but it's the only path to an actual streaming product).
Self-hosted library only — users upload/own their own files, you never touch anyone else's catalog. Legally clean, but it's a personal media player, not a Spotify competitor.

The Impact: If this ever gets real distribution, Google can and does get apps that scrape YouTube's internal API pulled from app stores, and no music company will acquire — or even seriously look at — a product whose core mechanism is bypassing the ToS of the platform whose data it's also scraping for metadata. This is the single fact that makes "top platforms want to buy this" false as currently built. The Problem: CORSMiddleware in main.py (lines 26–32):

allow_origins=["*"] combined with allow_credentials=True is invalid per the Fetch spec — browsers refuse to expose a response with a wildcard Access-Control-Allow-Origin to credentialed requests. Priority order

1. Kill the YouTube audio extraction in music_service.dart — replace with a legitimate preview.
This is the change that actually makes it a discovery app instead of a streaming app with extra steps. Apple's iTunes Search API is free, needs no key, and returns a real 30-second previewUrl per track — built for exactly this ("preview then send them to the store"), which is precisely the discovery model:

dart
import 'package:http/http.dart' as http;
import 'dart:convert';
import 'package:just_audio/just_audio.dart';

class MusicService {
  final AudioPlayer _audioPlayer = AudioPlayer();
  AudioPlayer get player => _audioPlayer;

  Future<void> playPreview(String title, String artist) async {
    final query = Uri.encodeComponent('$title $artist');
    final url = Uri.parse(
      'https://itunes.apple.com/search?term=$query&media=music&entity=song&limit=1',
    );
    try {
      final response = await http.get(url);
      if (response.statusCode != 200) throw Exception('iTunes lookup failed');
      final results = json.decode(response.body)['results'] as List;
      if (results.isEmpty) throw Exception('No preview found for $title');
      final previewUrl = results.first['previewUrl'] as String?;
      if (previewUrl == null) throw Exception('No preview URL for $title');
      await _audioPlayer.setUrl(previewUrl);
      _audioPlayer.play();
    } catch (e) {
      rethrow; // let the UI show a real error state instead of silently doing nothing
    }
  }

  void dispose() {
    _audioPlayer.dispose();
  }
}

Apple's terms require preview playback to sit "proximate to a store badge" — so wherever this preview plays in your existing UI, put a small "Listen on Apple Music" / "Open in Spotify" tap target next to it (step 2 covers the Spotify half). That requirement actually reinforces the discovery framing rather than fighting it.
